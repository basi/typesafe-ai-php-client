# Parity with the official Python SDK

Comparison against `typesafe-sdk` 0.7.5, the official Python client for the same API. This client
intentionally mirrors most of that SDK's HTTP behaviour, so that request formation and retry rules
are unsurprising to anyone coming from Python — but it diverges in a few places, called out below,
either to suit PHP or to make one specific consequence of retries (double-charging a probabilistic
POST) opt-in rather than a silent default.

The baseline moved from 0.7.1 to 0.7.5. The retry and error code of the official SDK (`retry.py`,
`errors.py`) is unchanged since 0.7.1, so the rows about retries and errors still hold, and rows
marked "(0.7.1 sync)" keep describing that release. What 0.7.5 added — images and Box questions —
is in the rows marked "(0.7.5 sync)", and what 0.7.2 to 0.7.5 changed but this client does not
mirror is in the last rows of the table.

| Feature | Python (`typesafe-sdk` 0.7.5) | This client (`basi/typesafe-ai-php-client`) | Note |
|---|---|---|---|
| Endpoints | `POST /v1/systemone`, `GET /v1/models` | Same | Full parity. |
| Auth | `Authorization: Bearer <key>` | Same | Full parity. |
| Per-attempt timeout | Yes, configurable | Yes: `ClientOptions::$timeoutSeconds` (default 30s), plus a separate `$connectTimeoutSeconds` (default 5s) | Full parity; this client additionally exposes the connect timeout on its own. |
| Retryable statuses | 408, 429, 5xx | Same: 408, 429, 500-599 (including 529 "overloaded") | Full parity. |
| Retryable exceptions | Connection errors, timeouts | Same, surfaced as `TransportException` / its subclass `TimeoutException` | Full parity. |
| Backoff | 0.5s × 2^attempt, capped at 5s, minus up to 25% random jitter | Same (`Http\RetryPolicy`) | Full parity. |
| `retry-after-ms` handling | Preferred over `Retry-After` | Same | Full parity. |
| `Retry-After` handling | Integer seconds, or an HTTP-date | Same | Full parity. |
| Server delay ceiling | A requested delay over 60s falls back to computed backoff | Same, and additionally configurable down from 60s via `ClientOptions::$maxRetryDelayMs` (default `null`, i.e. 60s, unchanged) | **Deliberate divergence.** The official SDKs only expose the fixed 60s ceiling. A caller with its own hard bound on call duration — for example a queue worker with a job timeout — can lower it further so a large server-requested delay cannot blow that bound; it cannot be raised above 60s. |
| `maxRetries` for `POST /v1/systemone` | Retried like any other request, with a small default retry count | **0 by default** | **Deliberate divergence.** A retried POST can be billed twice, and a System One answer is probabilistic, so a "successful" retry is not guaranteed to reproduce the original response. This client requires an explicit opt-in (`ClientOptions::$maxRetries`) before retrying a POST for any reason other than the 429 case below. |
| Retrying a rate-limited POST | Subject to the same retry count as anything else | **Always eligible for one retry**, via `ClientOptions::$retryRateLimitedPost` (default `true`) | **Deliberate divergence**, in the opposite direction: a 429 means the request was rejected *before* it was processed, so it cannot have been billed or answered — retrying it is safe even with `maxRetries: 0`. |
| `maxRetries` for `GET /v1/models` | Small default retry count | `ClientOptions::$modelsMaxRetries`, default 2 | Same idea; the endpoint is read-only, so there is no billing/probability concern and thus no divergence in spirit — the exact default count was simply chosen independently. |
| `User-Agent` | Identifies the SDK and its version | `typesafe-ai-php-client/<version>` | Full parity in intent. |
| SDK identification header | `X-TypeSafe-SDK` | Same | Full parity. |
| Runtime header | `X-TypeSafe-Runtime: python/<version>` | `X-TypeSafe-Runtime: php/<version>` | Full parity in intent. |
| Retry count header | `X-TypeSafe-Retry-Count`, present only on retries | Same | Full parity. |
| Request id | Read from `x-typesafe-request-id`; exposed on the response and on every API error | Same (`SystemOneResponse::requestId()`, `ApiException::getRequestId()`) | Full parity. |
| Error classes | One exception per status family: auth, not found, validation, rate limit, server | Same shape: `AuthenticationException`, `NotFoundException`, `ValidationException`, `RateLimitException`, `ServerException`, all extending `ApiException` | Full parity. |
| Unknown answer type | Skipped, with a warning logged | **Kept**, as `UnknownAnswer` (the raw decoded data is preserved) | **Deliberate divergence.** Silently dropping a future answer type is worse for a statically-typed consumer than an explicit "unknown" case; this client never discards part of a response body. |
| Unknown answer `confidence` | Not applicable (the answer itself is skipped) | Not applicable as a typed accessor; `UnknownAnswer::toArray()` / `raw()` exposes whatever the server sent, unmodified, including a `confidence` field if one is present | See above. |
| Configuration via environment variables | Reads an API key (and a few other settings) from the process environment automatically | **None.** The API key and every option are constructor arguments | **Deliberate divergence.** Implicit environment configuration is a common source of surprise in a library — for example, the wrong key being silently picked up from the process environment. This client always makes configuration explicit at the call site; reading an environment variable, if wanted, is left to the application (`Client::withGuzzle(getenv('TYPESAFE_API_KEY'))`). |
| Streaming responses | Not offered | Not offered | Full parity — there is nothing to diverge from. `POST /v1/systemone` always returns a single JSON document; the API has no streaming endpoint. |
| Mock/test HTTP client | Provided for the SDK's own test suite | `TypesafeAi\Testing\MockHttpClient`, shipped in `src/` | Broader parity: available to integrators' test suites, not just to this package's own tests. |
| Question set / result builder | Not offered | `TypesafeAi\Request\Questions`: a fluent builder that packs several questions into one request without naming the set, using positional wire keys (`question_0`, `question_1`, ...); decoded back into a tuple by `TypedSystemOneResponse` | This pattern originates in an unofficial Swift SDK, not the official Python one; included here because this client offers the same idea. |
| Typed results / `response_model` | Yes, via `response_model` (0.7.0+) | `TypedSystemOneResponse::decode()`: strictly matches each answer to its question's type, by position or by name | Full parity in intent: both fail fast when a response does not match the expected shape. |
| Parallel evaluation | All questions in a request are evaluated against the state in parallel, in one query (the vendor calls this its "parallel sampler") | Same — this is unchanged request/response behaviour; `Questions` and `Client::evaluate()` are sugar for packing more questions into one request instead of issuing one request per question | This is API behaviour, not an SDK feature: every SDK that talks to this API sends all of a request's questions in a single call. No SDK exposes sampling controls (seed, temperature, sample count), and answers remain probabilistic. |
| API key validation | 0.7.1: after trimming, rejects a key that is empty, non-ASCII, non-printable, or still contains whitespace | Same: `Client::__construct()` trims surrounding spaces and throws `\InvalidArgumentException` under the same conditions | Full parity (0.7.1 sync). |
| Credential redaction | 0.7.1: redacts the key from exception messages in its raw, `repr()`-escaped, and JSON-escaped forms; drops the original exception instead of chaining it | Same idea via `Http\Redactor`: redacts the raw key, `Bearer <key>` as one unit, the JSON-escaped form, and the URL-encoded form with `***`; `TransportException`/`TimeoutException` never chain the original exception | **Partial parity, deliberate divergence in which forms (0.7.1 sync).** PHP has no `repr()` equivalent, so this client redacts a URL-encoded form instead, which is more relevant to an HTTP client. Since the original exception is no longer available via `getPrevious()`, its class name is kept in the new message instead. |
| AI gateway configuration | Documented for OpenRouter and the Vercel AI Gateway, by overriding the base URL and default model | Same override points (`ClientOptions::$baseUrl`, `$defaultModel`) are exposed | **Untested divergence (0.7.1 sync).** Neither gateway has been exercised against this client; see README "Using an AI gateway". |
| Image constructors | `Image(data)` takes image bytes (or any buffer) or a path-like object; also `Image.from_base64()` and, with the `pil` extra, `Image.from_pil()`. An image is validated and read when the request is prepared, once, and kept | `Image::fromBytes()`, `Image::fromPath()`, `Image::fromBase64()` and, with ext-gd, `Image::fromGd()` | **Partial parity, deliberate divergences (0.7.5 sync).** A PHP string cannot say bytes from path, so the constructors are named. Bytes, base64 text and GD images are validated when the `Image` is created, earlier than in Python; a path is read lazily when a request first carries the image and kept after a successful read (a failed read is not remembered). `fromBase64()` is stricter than `base64_decode()`: unpadded text is rejected, as in Python. `fromGd()` encodes JPEG at quality 95 like `from_pil()`, and also PNG, GIF, WebP, BMP and AVIF where the GD build can (the API accepts PNG and JPEG only today, and rejects the rest). Paths only name local files: stream wrappers (`php://`, `file://`, `data:`) are rejected. No buffer objects, and no `format` argument (Python has none either). |
| Images in content | Assets placed anywhere in `state`, `instructions` or `criteria`, or formatted into a string, get a unique `<image:...>` reference; the SDK finds them while it serializes the request and uploads them | Same: `Image::jsonSerialize()` reports each image to a context that `json_encode()` runs inside, so an image is found wherever `json_encode()` meets it (arrays, objects, `JsonSerializable`, `ArrayObject`); the context is kept per fiber | **Full parity (0.7.5 sync).** An image that appears several times is uploaded once. PHP only: an image encoded by a nested `json_encode()` call made while the request is being encoded, such as one inside the caller's own `jsonSerialize()`, counts as placed in the request; the official SDK's serializer never meets an image in such a place. |
| Named assets | `assets=` argument of `system_one`: references of the caller's choosing | `assets:` argument of `SystemOneRequest`, `Questions::toRequest()` and `Client::evaluate()` | **Full parity in behaviour apart from one deliberate divergence (0.7.5 sync), in a different place.** `ClientInterface` is unchanged (a new parameter would break implementers and test doubles), so the assets are part of the request. As in Python, a named image placed in the content is written as its name and uploaded once; an image with two names is uploaded once per name; named assets are uploaded first. Python accepts any non-empty string as a name. PHP turns a numeric string such as `"1"` into the integer key `1` and cannot tell it from a position in a list, so an integer key, and a list such as `[$photo]`, are rejected with an `\InvalidArgumentException`; a name that PHP keeps as a string, such as `"007"` or `<1>`, is fine. |
| Attached assets | `client.attach_assets(assets)` context manager: calls inside the `with` upload each attached asset whose reference the request mentions; nests; safe across threads and tasks | `Client::attachAssets($assets, $callback)`: same, for the duration of the callback; holds are counted; fibers see the attachments | **Partial parity (0.7.5 sync).** PHP has no context manager, so it is callback-scoped, and only on `Client`, not on `ClientInterface`. Two attachments overlap without nesting only when fibers interleave. |
| Multipart upload | A request with assets is `multipart/form-data`: the JSON is the `request` part, each asset is an `asset-N` file part labelled by its signature (`image/png`, `image/jpeg`, else `application/octet-stream`), one part per name; the body is built once, so retries resend the same bytes | Same, byte for byte in layout | **Full parity (0.7.5 sync).** The client adds `'expect' => false` to the Guzzle client it builds, because Guzzle would otherwise send `Expect: 100-Continue` with bodies of 1 MiB or more and the official SDK's HTTP client never does. |
| Images header | The caller sends `TypeSafe-Danger-Zone-Images: true`, with `headers=` or `extra_headers=`; the SDK never adds it | Same: set `ClientOptions::$headers` or `extraHeaders`; the client never adds it, and has no constant for it | **Full parity (0.7.5 sync).** Without the header the API answers `400`. |
| Default and per-call headers | `headers=` on the client; `extra_headers=` on `system_one` and on `models.list`. Order: client headers, then the call's, then the SDK's own (`Authorization`, `Accept`, `User-Agent`, `X-TypeSafe-SDK`, `X-TypeSafe-Runtime`), then `Content-Type`; a supplied `X-TypeSafe-Retry-Count` is dropped | `ClientOptions::$headers` for every request, `models()` included; `SystemOneRequest::extraHeaders()` (also on `Questions::toRequest()` and `Client::evaluate()`) per call. Same order, compared without regard to case | **Partial parity (0.7.5 sync).** `ClientInterface` is unchanged, so per-call headers live on the request, and `models()` has no per-call headers. Header names (HTTP tokens) and values (no control characters) are validated when the objects are built, because a PSR-7 message otherwise throws from `withHeader()` outside the transport's error handling. |
| JSON content in question fields | `instructions`, `criteria` values and `true`/`false` take text, JSON values or assets (`Content`) | `instructions`, `whenTrue`/`whenFalse`, choice option descriptions and score levels take `string\|array\|object`, images included; `ScoreAnswer::legend()` can hold decoded JSON content too | **Full parity in what is accepted (0.7.5 sync); closes a gap that predates it.** The API schema in `spec/` already allowed JSON content there; this client only took text. Its own stricter rules stay: a string instruction or score level must not be empty, `instructions` is required for noul, choice and score questions, and option and level counts are checked. |
| Box and grouped answers | `Box` question, `BoxAnswer` (with `BoxCoordinates`), and `SystemOneResponse.nouls`, `.choices`, `.scores`, `.boxes` | `BoxQuestion` (`Questions::box()`), `BoxAnswer`, `BoxCoordinates`, `TypedSystemOneResponse::box()`, and `SystemOneResponse::nouls()`, `choices()`, `scores()`, `boxes()` | **Full parity (0.7.5 sync).** The groups are methods that filter on each call, not cached properties. A box answer is no longer an `UnknownAnswer`, which is a change for code that tested for one. |
| Asset errors | Everything invalid, before the request is sent, is a `TypeSafeError` | `\InvalidArgumentException` for an invalid object (library convention); `AssetException`, a `TypesafeAiException`, for an image that cannot be read when the request is sent, thrown before any HTTP request and never retried | **Deliberate divergence (0.7.5 sync).** A path image is valid until the file is read, which happens at send time, so that failure is not an argument error. Messages follow Python's: `Asset '<name>': Image file 'x.png' could not be read: No such file or directory.` |
| `extra_body` | `extra_body=` shallow-merges extra top-level fields into the body, and can replace `assets` | Not implemented | **Not implemented (0.7.5 sync).** The payload is only what `SystemOneRequest` describes. |
| Request body compression | 0.7.5 compresses bodies of 1,024 bytes or more with zstd by default, when available; the SDK's own tests note that the production API does not accept compressed bodies yet | Not implemented: bodies are sent as they are | **Not implemented (0.7.5 sync).** A PSR-18 client of your own could compress, but the production API does not accept it yet. |
| HTTP/2 | 0.7.2: an `http2` extra | N/A | **N/A (0.7.2).** Use your own PSR-18 client for HTTP/2. |
| Request validation, TLS and connection pool | 0.7.3: more request validation; fixes for TLS handshakes with `truststore`; keep-alive tuning | The validation is covered by the constructors' own checks; the rest is N/A | **N/A (0.7.3).** TLS and pooling belong to Guzzle and cURL here. |
| Non-finite numbers | 0.7.4: `NaN` and `Infinity` are serialized as strings | Not implemented: `json_encode()` throws a `\JsonException` | **Not implemented (0.7.4).** |
| Logging | Debug logs truncate large bodies, so images do not flood them | N/A: this client does not log | **N/A.** |
| OpenAPI snapshot | Models are generated from the live spec | `spec/` is refreshed from the live spec: it describes `Asset`, the Box schemas, the `assets` field and the `TypeSafe-Danger-Zone-Images` header | **Current (0.7.5 sync).** `composer spec:check` finds no drift, and the weekly workflow keeps it so. The spec also lists a `TypeSafe-Danger-Zone-Long-Context` header, which neither the official SDK nor this client uses. |

## Keeping this current

This table is a point-in-time comparison. If the official SDK's retry defaults, headers, or error
handling change, or this client's own OpenAPI snapshot drifts (`composer spec:check`, or the
weekly `spec-drift` workflow that opens a pull request when it detects a change), revisit this
table together with the affected DTOs and tests.
